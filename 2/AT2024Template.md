# **Спецификация требований программного обеспечения (SRS)**
# **Система контроля исполнения поручений (СКИП)**
# 1. Введение

Настоящий документ представляет собой Спецификацию требований к программному обеспечению (CTПO/ SRS) для корпоративной «Системы контроля исполнения поручений» (СКИП). Документ разработан в соответствии с рекомендациями стандарта IEEE Std 830-1993 и фиксирует исчерпывающий перечень функциональных и нефункциональных требований, необходимых для проектирования, разработки, тестирования и ввода системы в эксплуатацию.
## Цели

Основная цель документа — установить однозначное, верифицируемое и согласованное понимание поведения системы между Заказчиком (руководством предприятия) и командой разработки.

Документ определяет:

·        Функциональные и нефункциональные требования к системе.

·        Границы применения системы.

·        Ограничения, предположения и зависимости, влияющие на реализацию.

·        Основу для последующего проектирования, разработки и тестирования.

Аудитория документа:

·        Заказчик — руководство предприятия, формулирующее бизнес-требования и принимающее систему в эксплуатацию;

·        Бизнес-аналитики — для уточнения и трассировки требований;

·        Команда разработки (архитекторы, разработчики, проектировщики БД) — для проектирования и реализации;

·        Команда тестирования — для разработки тест-кейсов и проверки соответствия;

·        Служба эксплуатации и сопровождения — для развёртывания, поддержки и развития системы.

## Границы применения

Программная система «СКИП» является специализированным корпоративным решением, предназначенным для автоматизации процессов выдачи, иерархического делегирования, декомпозиции, исполнения и каскадного контроля поручений на предприятии с древовидной организационной структурой.

**Система обеспечивает:**

- назначение поручений руководителями любых уровней своим непосредственным подчинённым;
    
- каскадное делегирование поручений вниз по иерархии;
    
- декомпозицию полученного поручения на несколько подзадач с назначением каждому прямому подчинённому и автоматическим закрытием родительского поручения только после выполнения всех дочерних;
    
- фиксацию выполнения поручений с кратким отчётом;
    
- мотивированный отказ исполнителя от поручения с уведомлением постановщика;
    
- уведомление постановщика об отсутствии исполнителя (отпуск, больничный, иное);
    
- согласование отчётов на каждом уровне иерархии;
    
- доведение отчёта о выполнении до инициатора поручения.
    

**Документ не распространяется на:**

- бухгалтерский и кадровый учёт предприятия;
    
- системы электронного документооборота общего назначения;
    
- полнофункциональные системы управления проектами (планирование ресурсов, диаграммы Ганта, управление портфелем проектов). Декомпозиция поручений в СКИП ограничена иерархией подчинения и не заменяет проектного управления.

# 2. Общее описание

  

## Описание изделия

### **Интерфейсы системы**

СКИП является компонентом корпоративной ИТ-инфраструктуры и взаимодействует со следующими смежными системами:

- **Кадровая учётная система (1С:ЗУП / SAP HR)** — источник организационно-штатной структуры: подразделений, должностей, руководителей и непосредственной подчинённости сотрудников.

- **Корпоративная служба каталогов (Active Directory / OpenLDAP)** — централизованная аутентификация и Single Sign-On (SSO).

- **Корпоративный почтовый сервер (Exchange / Postfix)** — транспортный канал для уведомлений о статусах поручений.


### **Интерфейсы пользователя**

Доступ пользователей осуществляется исключительно через веб-интерфейс в современных браузерах. Пользовательский интерфейс адаптирован под различные разрешения экранов (от 1280x720 до 4K), поддерживает клавиатурную навигацию и обеспечивает разделение рабочей области на смысловые блоки: панель субординации, списки поручений, форму создания и карточку каскадного отчета.
### **Интерфейсы аппаратных средств ЭВМ**

Специальные аппаратные модули не требуются. Серверная часть развертывается на стандартных виртуальных или физических серверах архитектуры x86-64. Клиентские рабочие места используют стандартные офисные ПК.
### **Интерфейсы программного обеспечения**

СКИП использует следующие системные программные интерфейсы:

- СУБД PostgreSQL версии 14 и выше для надежного транзакционного хранения данных.
    
- LDAPS (Lightweight Directory Access Protocol over SSL/TLS) на порту 636 для аутентификации.
    
- SMTP / SMTPS на портах 25/465/587 для отправки электронных писем.
    
- RESTful API (JSON over HTTPS) для периодической синхронизации оргструктуры.

### **Интерфейсы коммуникаций**

Все взаимодействие между клиентом и сервером СКИП осуществляется по защищенному протоколу HTTPS с использованием криптографических протоколов TLS 1.2 и TLS 1.3. Применение незащищенного протокола HTTP запрещено на уровне конфигурации сетевых шлюзов.

### **Ограничения памяти**

Специальные требования к объёму оперативной и постоянной памяти для СКИП не предъявляются. Серверная часть развёртывается на стандартных виртуальных или физических серверах архитектуры x86-64; клиентская часть функционирует в стандартных современных браузерах. Требования к производительности и утилизации ресурсов определены в разделе «Производительность» (подлежат уточнению).

### **Действия**

Система функционирует в круглосуточном режиме (24/7). Регламентные работы (синхронизация организационной структуры, резервное копирование БД) выполняются в ночное окно и не должны прерывать активные пользовательские сессии. Детальные сценарии эксплуатации, периодичность фоновых задач и параметры эскалации определены в функциональных требованиях FR-SYS-01 и FR-SYS-02 (раздел 3.1.4).

## Функции изделия

Перечень функций СКИП:

- **Управление организационной иерархией** — отображение структуры подчинения.
- **Создание поручения** — руководитель формирует поручение (описание, срок) и назначает его только своему непосредственному подчинённому.
- **Получение поручения** — сотрудник видит назначенные ему поручения.
- **Выполнение поручения самостоятельно** — отметка о выполнении, краткий отчёт.
- **Делегирование поручения** — переназначение поручения только своему непосредственному подчинённому.
- **Уведомление постановщика** — при выполнении поручения уведомляется тот, кто непосредственно назначил поручение данному сотруднику.
- **Согласование отчёта** — постановщик видит отчёт и может подтвердить его либо исправить и передать выше.
- **Движение отчёта вверх по иерархии** — на каждом уровне отчёт может быть подтверждён либо исправлен и передан выше.
- **Достижение инициатора** — отчёт (исправленный или неисправленный) доходит до самого верхнего уровня — до того, кто изначально сформулировал поручение.
- **История поручения** — просмотр всей цепочки делегирования и согласования.
- **Уведомления** — оповещения о новых поручениях, выполнении, правках, подтверждениях.

## Характеристики пользователей

В системе выделяются следующие классы пользователей, обусловленные иерархией предприятия:

| Класс пользователя                                             | Положение в иерархии                                    | Роль в СКИП                                                                                                        |
| -------------------------------------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Директор                                                       | Вершина иерархического дерева (нет вышестоящих)         | Инициатор корневых поручений; финальный утверждающий итогового отчёта                                              |
| Руководитель среднего звена (Департамент / Управление / Отдел) | Промежуточные звенья (имеют руководителя и подчинённых) | Исполнитель, делегирующий или декомпозирующий поручение; согласующий отчёт (правка или подтверждение)              |
| Линейный сотрудник                                             | Нижний уровень (нет подчинённых)                        | Конечный исполнитель; автор отчёта; субъект права мотивированного отказа                                           |
| Системный администратор                                        | Служебная роль вне управленческой цепочки               | Синхронизация оргструктуры, аудит безопасности, управление системными параметрами (без доступа к тексту поручений) |

## Ограничения

Разработка и эксплуатация СКИП подпадают под следующие дисциплинарные и нормативные ограничения:

- **Защита персональных данных:** обработка ПДн сотрудников должна соответствовать требованиям Федерального закона № 152-ФЗ «О персональных данных».

- **Корпоративные стандарты информационной безопасности:** система должна соответствовать действующим политикам ИБ предприятия (разграничение доступа, парольная политика, журналирование).

- **Архитектурные ограничения:** система должна быть реализована в рамках трёхзвенной клиент-серверной архитектуры; прямой доступ клиентских приложений к БД не допускается.

  

## Предположения и зависимости

Требования к СКИП сформулированы на основе следующих предположений:

- Организационная структура предприятия строго древовидна: у каждого сотрудника (кроме Директора) существует ровно один непосредственный руководитель.
    
- Кадровая служба предприятия своевременно отражает кадровые переводы и увольнения во внешней кадровой системе.
    
- Корпоративная служба каталогов Active Directory доступна непрерывно для валидации учетных записей.

# 3. Детальные требования

## Функциональные требования

### 3.1 Функциональные требования по классам пользователей (ролям)

#### 3.1.1 Класс «Руководитель верхнего уровня (Директор)»

**Требование FR-DIR-01: Первичная постановка поручения высшим руководством**

|Параметр|Содержание|
|---|---|
|**Идентификатор и название**|FR-DIR-01: Первичная постановка поручения высшим руководством|
|**Предусловие**|Директор аутентифицирован; оргструктура актуальна (FR-SYS-01).|
|**Входные данные и валидация**|1. Заголовок (5–200 симв., обязательное).  <br>2. Описание задачи (10–4000 симв., обязательное).  <br>3. Срок исполнения (дата/время, обязательное; дедлайн > текущее время + 2 часа).  <br>4. Исполнитель — только прямой подчинённый Директора (начальник департамента).  <br>5. Вложения — согласно таблице 3.1-B.|
|**Обработка**|1. Проверка, что адресат — прямой подчинённый Директора.  <br>2. Создание корневого поручения со статусом «Назначено», фиксация автора (Директор) и времени создания.  <br>3. Сохранение вложений.  <br>4. Уведомление исполнителя о назначении.|
|**Выходные данные**|1. Уведомление Директору об успешном создании.  <br>2. Поручение в реестре «Выданные мной».  <br>3. Уведомление назначенному исполнителю.|
|**Исключительные ситуации**|E-01: выбран не прямой подчинённый — операция блокируется.  <br>E-02: дедлайн в прошлом — операция блокируется.  <br>E-03: превышены ограничения вложений (таблица 3.1-B) — операция отменяется.|
|**Приоритет и проверка**|Приоритет 1 (обязательное). Проверка: сквозное автоматизированное тестирование.|

**Требование FR-DIR-02: Мониторинг дерева делегирования и статусов поручения**

|Параметр|Содержание|
|---|---|
|**Идентификатор и название**|FR-DIR-02: Мониторинг дерева делегирования и статусов поручения|
|**Предусловие**|Директор открыл карточку созданного им поручения.|
|**Входные данные**|Идентификатор корневого поручения.|
|**Обработка**|1. Система извлекает все дочерние поручения по цепочке вниз.  <br>2. Строится дерево прохождения задачи по уровням оргструктуры.  <br>3. Для каждого узла выводятся: статус (таблица 3.1-A), ФИО ответственного, дедлайн, время в текущем статусе.|

### 3.2 Требования логики базы данных (Logical Database Requirements)

NFR-LDB-01. Сущности БД
Система должна хранить следующие логические сущности и связи между ними:

|Сущность|Назначение|Ключевые связи|
|---|---|---|
|**Сотрудник**|Узел иерархии|ровно один непосредственный руководитель (кроме Директора); произвольное число подчинённых; одно подразделение; учётная запись; признак активности|
|**Подразделение**|Узел организационной иерархии (департамент / управление / отдел)|одно родительское подразделение (кроме корневого); руководитель — сотрудник этого подразделения|
|**Поручение**|Базовая сущность задачи|автор (инициатор), постановщик, исполнитель; ссылка на родительское поручение (кроме корневого); описание, срок, статус, тип (одиночное / составное / дочернее)|
|**Отметка о выполнении (отчёт)**|Результат исполнения|1:1 с дочерним поручением; текст отчёта, автор, время фиксации|
|**Версия отчёта**|Каждая правка согласующего|ссылка на отчёт; автор правки, номер ревизии, текст «до/после», комментарий|
|**Согласование**|Действие согласующего на уровне каскада|ссылка на поручение и версию отчёта; тип действия (подтверждение / правка)|
|**Отсутствие сотрудника**|Период нетрудоспособности|ссылка на сотрудника; тип отсутствия, период, источник (HR-система)|
|**Журнал аудита**|Неизменяемая последовательность событий|ссылка на поручение; субъект действия, тип действия, значения «до/после», метка времени|

**NFR-LDB-02. Ограничения целостности иерархии.** Система должна обеспечивать:

- у каждого сотрудника, кроме Директора, ровно один непосредственный руководитель;

- отсутствие циклов в графе подчинения;

- у каждого подразделения, кроме корневого, ровно одно родительское подразделение;

- сотрудник относится ровно к одному подразделению;

- руководитель подразделения — сотрудник этого подразделения.


**NFR-LDB-03. Ограничения целостности поручений.** Система должна обеспечивать:

- у каждого поручения ровно один инициатор и ровно один постановщик;

- исполнитель — прямой подчинённый постановщика (ТЗ, п. 3.2);

- дочернее поручение имеет ровно одно родительское; корневое — не имеет;

- срок дочернего поручения не превышает срок родительского;

- составное поручение имеет не менее двух дочерних;

- запрет декомпозиции поручения в финальном статусе («Утверждено и закрыто», «Отклонено исполнителем»);

- запрет циклов в дереве поручений (поручение не может быть родителем самого себя).


**NFR-LDB-04. Ограничения целостности отчётов и согласования.** Система должна обеспечивать:

- отчёт существует только для поручения в статусе «В работе», «На согласовании», «На доработке» или «Утверждено и закрыто»;

- не более одного отчёта на поручение (1:1);

- версии отчёта нумеруются последовательно, без пропусков, с сохранением исходного и изменённого текста;

- запись согласования ссылается на конкретную версию отчёта и сотрудника-согласующего;

- запрет удаления отчёта, версии или записи согласования, на которые ссылаются незавершённые поручения;

- отказ исполнителя фиксируется с обязательной мотивировкой и не удаляется.


**NFR-LDB-05. Ограничения целостности отсутствий.** Система должна обеспечивать:

- запись об отсутствии относится ровно к одному сотруднику;

- дата окончания не раньше даты начала;

- тип отсутствия — из фиксированного перечня (отпуск, больничный, иное);

- периоды отсутствия одного сотрудника не пересекаются (несколько записей допускается).

**NFR-LDB-07. Срок хранения данных.** Поручения, отчёты, версии отчётов, записи согласования и журнал аудита хранятся не менее [подлежит уточнению] лет с момента создания с возможностью просмотра в течение этого срока.
