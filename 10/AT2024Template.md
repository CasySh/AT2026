# 1. Введение

Настоящий документ представляет собой спецификацию требований к программному обеспечению (SRS) системы адресной рассылки сообщений с фильтрацией получателей, действующей в пределах крупной административной единицы (крупный город, область).

## Цели

Целями разработки системы являются:

* автоматизация определения получателей уведомлений по геопространственным и демографическим критериям;
* сокращение времени оповещения населения при чрезвычайных ситуациях (ЧС);
* обеспечение создания, хранения и повторного использования шаблонов оповещения;
* предоставление коммерческим клиентам сервиса адресных рассылок с предварительным расчетом стоимости и автоматическим формированием финансовой отчетности;
* централизованное управление нормативно-справочной информацией (НСИ), ролевыми моделями и учетными записями пользователей.

## Границы применения

Документ распространяется на систему массового и адресного оповещения населения региона. Система обеспечивает получение обезличенных сведений о населении из внешней ИС, выборку целевых групп по заданным фильтрам, расчёт стоимости коммерческих услуг, ведение справочников и передачу сообщений на внешний SMS-шлюз.

Поддерживаемые сценарии использования:

- **Экстренное оповещение (МЧС)**: геопространственный (радиус, полигон, сота), демографический или спец-статусный отбор получателей без тарификации с приоритетной отправкой;
- **Коммерческая рассылка**: конструирование шаблона клиентом, предпросмотр охвата, предварительный и окончательный расчет стоимости, формирование счетов и актов;
- **Администрирование**: ведение справочников (категории, тарифы, роли), регистрация и модерация пользователей, аудит действий.

В границы Системы не входят: физический прием денежных средств (формируются только финансовые документы), первичный учет населения и физическая доставка SMS-сообщений операторами связи.

# 2. Общее описание

## Описание изделия

- **Интерфейсы системы**: Веб-приложение (Single Page Application), доступное через веб-браузер. Включает графическую карту административной территории, панель управления шаблонами, конструктор таргетинга, личный кабинет коммерческого клиента и консоль администратора.
- **Интерфейсы ПО**: Взаимодействие с внешними картографическими сервисами (Яндекс.Карты, 2GIS), API геокодирования, внешней ИС учета населения (REST) и внешним SMS-шлюзом (SMPP).
- **Интерфейсы коммуникаций**: HTTPS (TLS 1.2+) для клиент-серверного обмена, защищенный REST API и SMPP для внешних интеграций.
- **Ограничения памяти**: Максимальное количество хранимых шаблонов — 1000 единиц.

## Функции изделия

### Управление шаблонами

Создание, редактирование, удаление, разделение на категории «Экстренные» и «Коммерческие».

### Управление данными абонентов

Прием и хранение обезличенных профилей (пол, возраст, геолокация по вышке, спецпризнаки) без ПДн (ФИО, телефоны).

### Формирование целевых групп

Выборка аудитории по геозонам (радиус, полигон, сота), демографии и дополнительным признакам; предварительный расчет охвата.

### Массовое оповещение

Запуск экстренных рассылок МЧС и коммерческих рассылок с контролем статуса доставки в реальном времени.

### Коммерческий модуль

Расчет предварительной и окончательной стоимости рассылок по действующему тарифу, формирование актов и финансовых отчетов.

### Администрирование и аудит

Ведение НСИ (категории, тарифы, роли), модерация учетных записей, протоколирование действий пользователей.

## Характеристики пользователей

| Пользователь | Описание и функции | Влияние на требования |
|---|---|---|
| **Оператор МЧС** | Базовый пользователь. Отвечает за оперативный запуск экстренных рассылок при ЧС. | Минимальное количество действий для запуска («одна кнопка»), готовые шаблоны, высокий приоритет операций. |
| **Коммерческий клиент** | Продвинутый пользователь. Создает рекламные/информационные кампании, анализирует охват и расходы. | Личный кабинет, конструктор таргетинга, финансовая отчетность, ограничение доступа к точным геоданным. |
| **Администратор** | Инженер-администратор. Управляет НСИ, учетными записями, ролевыми моделями и интеграциями. | Консоль администрирования, гибкая настройка RBAC, подробное логирование. |
| **Конечный абонент** | Житель региона. Пассивный получатель SMS-сообщений. | Полная обезличенность данных (защита ПДн). |

## Ограничения

* Запрет на хранение и обработку ПДн (ФИО, паспортные данные, номера телефонов в открытом виде).
* Точность определения геолокации ограничена радиусом действия сотовой вышки (не точнее 100 м).
* Вход в систему коммерческих клиентов осуществляется строго после прохождения модерации Администратором.
* Физическая приемка платежей системой не выполняется (только формирование счетов и актов).
* Хранение истории рассылок и журналов аудита — не менее 5 лет.

## Предположения и зависимости

**Предположения:**

- Внешняя ИС корректно передает актуальные обезличенные данные абонентов.
- За каждым абонентом закреплено одно основное мобильное устройство.
- Серверная инфраструктура и каналы связи предоставляются Заказчиком и обеспечивают требуемую пропускную способность.

# 3. Детальные требования

Перед описанием детальных требований устанавливается единый формат описания каждого требования. Каждое требование в настоящем документе включает следующие атрибуты, выделенные жирным шрифтом для однозначной идентификации:

**Требование ID** — уникальный идентификатор требования (например, R3.01.01).
**Группа** — иерархическая категория, к которой относится требование.
**Описание** — текст требования, описывающий поведение системы или ограничение.
**Приоритет** — степень важности реализации (1 — высокий, 2 — средний, 3 — низкий).
**Риск** — уровень риска при нереализации или некорректной реализации (C — критический, H — высокий, M — средний, L — низкий).

Ниже приведены детальные требования, сгруппированные по категориям.

## 3.1. Функциональные требования

### 3.1.1. Управление шаблонами и выборка аудитории

**Требование ID**: R3.01.01
**Группа**: Функциональные требования \ Управление шаблонами
**Описание**: Система должна обеспечивать создание, редактирование и хранение шаблонов оповещений. Шаблон должен включать наименование, текст сообщения, критерии отбора (демография, место жительства, геозона, спецпризнаки) и настраиваемые параметры (координаты, радиус).
**Приоритет**: 1
**Риск**: C

**Требование ID**: R3.01.02
**Группа**: Функциональные требования \ Управление шаблонами \ Ограничения
**Описание**: Система должна хранить не более 1000 активных шаблонов. Редактирование и удаление шаблонов разрешено только пользователям с соответствующим правом доступа.
**Приоритет**: 1
**Риск**: C

**Требование ID**: R3.01.03
**Группа**: Функциональные требования \ Территориальные критерии
**Описание**: Система должна поддерживать задание геозон отбора на интерактивной карте: окружность (точка и радиус), произвольный полигон, область покрытия сотовой вышки.
**Приоритет**: 1
**Риск**: H

**Требование ID**: R3.01.04
**Группа**: Функциональные требования \ Дополнительные признаки
**Описание**: Система должна поддерживать динамически расширяемый перечень дополнительных признаков абонентов (например, наличие воинского учета, статус сотрудника экстренных служб) без изменения исходного кода программного обеспечения.
**Приоритет**: 1
**Риск**: H

**Риск**: C

**Группа**: Функциональные требования \ Данные абонентов \ Хранение
**Описание**: Система должна хранить для каждого абонента только обезличенные атрибуты: пол, возрастной диапазон, код района проживания, идентификатор текущей сотовой вышки и дополнительные признаки.
**Приоритет**: 1
**Риск**: C

**Требование ID**: R3.02.03
**Группа**: Функциональные требования \ Данные абонентов \ Геолокация
**Описание**: Система должна определять текущее местоположение абонента по последней зарегистрированной сотовой вышке и выводить информацию о возможной погрешности в окне предпросмотра аудитории.
**Приоритет**: 1
**Риск**: H

**Требование ID**: R3.02.04
**Группа**: Функциональные требования \ Данные абонентов \ Актуализация
**Описание**: Система должна обновлять данные об абонентах в режиме, близком к реальному времени (near real-time), по мере их поступления от внешней ИС.
**Приоритет**: 2
**Риск**: M

**Приоритет**: 1

**Приоритет**: 1
**Риск**: H

**Требование ID**: R3.04.02
**Группа**: Функциональные требования \ Мониторинг \ Отчетность
**Описание**: Система должна вести статистику рассылок (планируемый охват vs фактический по данным SMS-шлюза) и формировать сводные отчеты за выбранный период с функцией выгрузки в машиночитаемом формате (CSV/JSON/PDF).
**Приоритет**: 1
**Риск**: H

**Приоритет**: 1

## 3.6. Требования к пользовательской документации

Система должна поставляться со следующим комплектом документации:

* Руководство оператора МЧС (экстренные рассылки, работа с картой).
* Руководство коммерческого клиента (работа в личном кабинете, рассылки, финансы).
* Руководство администратора (управление НСИ, учетными записями, ролями и логами).
* Описание API интеграции (коннекторы внешней ИС и SMS-шлюза).

## 3.7. Используемые компоненты

Система разрабатывается с использованием следующего стека программных компонентов:

* **СУБД**: PostgreSQL 14+ (с расширением PostGIS для геопространственных запросов).
* **Backend**: Node.js / Python (FastAPI) с поддержкой асинхронной обработки очередей (Redis/RabbitMQ).
* **Frontend**: React / Vue.js (Single Page Application) с библиотекой OpenLayers / Leaflet для карт.
* **Веб-сервер**: Nginx (Reverse Proxy, TLS termination).

## 3.8. Интерфейсы

### Пользовательские интерфейсы

* **Контур МЧС**: Оптимизированный интерфейс с акцентом на скорость, картографическую визуализацию и быстрый запуск шаблонов.
* **Контур Коммерческий**: Личный кабинет с аналитическими дашбордами, конструктором таргетинга и разделом финансовых документов.
* **Контур Администрирования**: Табличный интерфейс управления НСИ, пользователями и журналом безопасности.

### Программные интерфейсы (API)

* **API Внешней ИС**: REST/JSON интерфейс для импорта обезличенных сведений о населении.
* **API SMS-шлюза**: Протокол SMPP v3.4 для высокоскоростной передачи SMS и получения статусов доставки.
* **Картографический API**: REST/WMS для получения тайлов карт и геокодирования (Яндекс.Карты / 2GIS).

### Коммуникационные интерфейсы

Обмен данными в сети выполняется по защищенным каналам с использованием шифрования TLS 1.2/1.3. При необходимости взаимодействия между ЦОД применяется IPsec VPN.
